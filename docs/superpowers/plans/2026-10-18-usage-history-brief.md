## Request (from the owner, paraphrased)
"In the watchdog, add a log of when the instance started and when it stopped, and the reason it stopped: the Destroy button, idle timeout, or the failsafe." The "watchdog" here is the whole auto-stop machinery: the web service lifecycle (apps/core/src/lifecycle.ts, agent.ts, registry.ts) plus the instance agent (instance/agent/vastcomfy_agent: idle.py, deadlines.py, destroyer.py, destroy_flow.py, state.py with destroy reasons idle_timeout, failsafe_deadline, manual, watchdog, ...) and instance/failsafe.sh (standalone failsafe).

## Behaviour to build
1. A persistent, bounded history of instance sessions kept by the web service (JSON file next to the registry, atomic write, like apps/core/src/console.ts persistence; path from config, e.g. USAGE_LOG_PATH set in docker-compose.yml to the data volume like BOOT_LOG_PATH; bounded by USAGE_LOG_MAX_ENTRIES default 200). One entry per instance: instance id, label/hostname, gpu name, price per hour (dph), started_at (when Start was accepted), ready_at (when it became ready, if it did), ended_at, duration, estimated cost (duration x dph, clearly an estimate), started_by (the user name from the session, never an email/secret), stop `reason`, and `stop_by` (user name) when it was the Destroy button.
2. Stop reason values (fixed enum, document in OpenAPI): `destroy_button` (Destroy from the web, record who), `idle_timeout`, `failsafe_deadline` (instance failsafe or agent deadline), `hard_cap`, `boot_failed` (instance destroyed itself because boot failed or Start failed), `gone` (instance vanished and the cause is unknown, e.g. Vast removed it), `extended`-type events are NOT stop reasons. Decide the reason like this: if the web service itself destroys the instance, it knows (`destroy_button`). If the instance disappeared by itself, infer from the LAST agent status the web saw: the agent reports idle_destroy_at, failsafe and hard-cap deadlines and a state; if the last known idle/failsafe/hard-cap deadline had passed (allow a small slack from config) pick that reason; if the last known agent state was a destroy state with a reason (see state.py), use it; otherwise `gone`. Prefer exact information from the agent over inference: check what /status (apps/core/src/agent.ts, contracts) exposes, and if the agent can cheaply record "destroying: <reason>" in its state and status BEFORE calling Vast destroy (instance side), add that (agent code + tests + contracts) so the web's last poll can pick it up; also print one line `[watchdog] destroying instance: reason=<reason>` to stdout (visible in Vast container logs / boot console), never containing secrets.
3. Also add log lines to the web service log (the existing structured logger, only the error name policy applies: no secrets) at Start and at stop: start (gpu, dph, who) and stop (reason, duration).
4. API: `GET /api/history` (admin only, no-store, same rules as other admin routes) returning the newest entries first, with `active` flag for the running one; OpenAPI updated; strict response shape.
5. Page: an admin-only "History" card (collapsible like the boot console card: see index.html console-toggle for the pattern, with the remembered choice in storage) listing recent sessions: start time, duration, GPU, reason in plain words ("Destroy button (by <name>)", "Idle timeout", "Failsafe deadline", "Hard cap", "Boot failed", "Disappeared"), estimated cost; textContent only; refresh when the state changes to none/ready, no tight polling.
6. Config only through contracts/config-schema.yaml + .env.example + apps/core/src/config.ts. Lint: python3 scripts/check_config_usage.py apps instance.
